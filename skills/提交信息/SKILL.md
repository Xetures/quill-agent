# 提交信息

## 先看清改了什么

1. 用 `list_dir` / `search_files` 摸清这次涉及哪些文件。
2. 用 `read_file` 读关键改动点。**不要只看文件名就下结论** ——
   文件名说明不了「为什么改」，而提交信息里最有价值的就是那个「为什么」。
3. 如果改动跨了好几个不相关的模块，先提醒用户：建议拆成多次提交，别包在一起。

## 结构

```
<类型>: <一句话说清做了什么>

<可选正文：为什么这么做。如果「怎么做」一眼看不出来，这段就是必须的>
```

类型只用下面这几个：

| 类型 | 用在 |
| --- | --- |
| `feat` | 新增能力 |
| `fix` | 修掉一个错误行为 |
| `refactor` | 行为不变，只改结构 |
| `docs` | 只改了文档或注释 |
| `test` | 只改了测试 |
| `chore` | 依赖、构建、配置 |

## 硬规矩

- 标题**说结论不说过程**：写「修复空回答导致界面空白」，不写「修改 agent.py 的循环」。
- 标题不超过 50 个字符，结尾不加句号。
- 不用「优化」「完善」「调整」这类没有信息量的动词 —— 它们等于什么都没说。
- 一次提交只讲一件事。

## 输出

先给一行推荐信息，再用一个短列表说明「哪部分对应改动里的哪块」，方便用户核对。
