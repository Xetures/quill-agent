# 代码审查

## 先取证，再下结论

不要凭印象评论。动手之前先把这几件事做实：

1. 用 `search_files` 找到涉及的模块，再用 `read_file` 读**完整**实现 ——
   只看片段很容易漏掉「这里默认它一定不为空」这类隐含前提。
2. 用 `search_content` 找出所有调用点：一个函数改得对不对，取决于谁在调它。
3. 用 `list_dir` 确认有没有对应的测试文件，有就一起读。

某个结论如果确认不了，就明说「这一点要看 X 才能判断」，不要猜。

## 按这五个角度过一遍

| 角度 | 具体找什么 |
| --- | --- |
| 正确性 | 边界条件、空值、异常路径。有没有「假设它一定存在 / 一定不为空」的地方？ |
| 契约 | 改了签名但调用方没跟着改？返回值语义变了？异常类型变了？ |
| 重复 | 同样的逻辑别处是不是也有一份？改了一处、漏了另一处？ |
| 性能 | 循环里做 I/O？O(n²) 的查找？每个元素都重新读一遍文件？ |
| 可读性 | 命名说的是「是什么」还是「怎么做」？有没有非要注释才看得懂的段落？ |

## 输出格式

按严重程度分三组，组内按文件顺序排列：

- **必须改**：会出错、会丢数据、有安全问题
- **建议改**：不影响正确性，但会埋雷
- **可选**：风格偏好

每条都要给出四样东西：**问题** + `文件:行号` + **为什么是问题**（会造成什么后果）
+ **怎么改**。

没有问题的角度**直接不提**，不要为了凑数写「这部分写得不错」。宁可短，不要全。
